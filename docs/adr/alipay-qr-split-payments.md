# 支付宝订单码支付（alipay_qr）与超额拆单

## 背景

个人支付宝（无营业执照）签约「订单码支付」（`alipay.trade.precreate`，产品码
`QR_CODE_OFFLINE`）后，支付宝限制单笔 ≤ ¥2000、单日 ≤ ¥20000。订单经常超过 ¥2000。

## 决定

- 支付渠道后台里「支付宝」渠道多了「支付宝产品」：网站支付（原 `alipay_page`，
  电脑/手机自动选 page/wap）或订单码支付（`alipay_qr`）。同一渠道可以来回切换。
- 订单码渠道可设：单笔上限、单日上限（北京时间自然日，0 = 不限）、超额自动拆单、
  最多拆成几笔（2–20，默认 10）。存在 `payment_channels` 的
  `per_payment_max_minor` / `daily_max_minor` / `split_enabled` / `split_max_parts`。
  其他支付方式不受这些设置影响。
- 单日上限是体验护栏，不是资金护栏（真正的限额在支付宝，超了支付宝拒付，已付的笔会在
  过期时自动退回）。估算口径：该渠道北京时间今天按实际付款时间的成功收款 + 该渠道上
  「未过期、未付清、已开始拆单」订单的剩余未付金额 + 本单 > 上限，这一单就不显示这个渠道；
  其他渠道照常显示。只在创建付款（拆单即首笔）时判断，后面的分笔不再检查；钱包充值同口径
  只检查不拆单。超过单笔上限又没开拆单（或要拆的笔数超过上限）同样不显示。
- 拆单的应付总额按「每一笔都要交自己的手续费」反推（固定费每笔一次、比例费每笔单独取整），
  保证 总额 − 各笔手续费之和 ≥ 货款；结账页和服务端用同一个函数。拆分计划（笔数、每笔金额、
  手续费快照）在首笔创建时冻结，之后后台改上限不影响在途订单。
- 拆单：N = ceil(应付 / 单笔上限)，按分平均拆，前面的笔多 1 分
  （3000 → 1500+1500；4001 → 1333.67+1333.67+1333.66）。每笔是独立的支付宝交易
  （`payment_split_parts`，商户订单号 = 行 id 去横线）。第 1 笔付完后自动生成第 2 笔的二维码。
- 订单只有一条整单付款记录（`payment_attempts`，金额 = 整单，`split_part_count` = 笔数，
  `processing_fee_minor` = 各笔手续费之和，商户号是 `split:<id>`）。全部笔付完才走原来的
  「已付款 → 发货」流程，所以发货、邮件、返利、利润、Telegram、日报都只看到一笔整单付款。
- 截止时间：最后一笔在订单到期那一刻或之后才付（哪怕过期任务还没跑）一律不发货；
  「已付款」的那一步数据库更新本身带 `expires_at > now` 条件，不满足整批回滚，之后过期、
  已付各笔自动退款并告警。
- 有效期：拆单订单每笔给 15 分钟，最多 2 小时，不会比原来的短（GPT 升级补差价单不延长，
  它受报价票据限制）。每笔二维码的支付宝 `timeout_express` 取订单剩余整分钟数（向下取整），
  所以二维码不会比订单活得久；订单过期后定时任务再主动 `alipay.trade.close` 一次。
- 没付完就过期/取消：已付的笔由每分钟的定时任务自动 `alipay.trade.refund` 原路退回
  （`payment_split_refunds`，行 id 即 `out_request_no`，重试不会重复退），成功后在 Telegram
  老板群「orders」话题报一条；支付宝拒绝退款（或网络错误重试 3 次仍失败）就标「manual」、
  报警，留给人工处理。永远不发货。
- 已过期订单的某一笔晚到的付款回调：记为 `rejected` 回执 + 整单付款记录
  `failure_code='split_late_payment'`（原有的待核对路径），不发货，同样自动退款并报警。
- 后台对已付款的拆单订单退款：退款金额从最后一笔往前分摊到各笔，每笔单独原路退。
- 钱包充值走订单码渠道时只校验上限，不拆单。

## 未做

- 不改其他支付方式；不改代理站（agent-shop）。
- 源渠道（易支付「支付宝」）没有设专属价的商品，两个渠道都按基础价，再各自按自己的费率加价；
  如果易支付渠道费率不是 0，这类商品两边价格会不同。
